# FoodLens 食光偵探｜單班四週試辦執行包 v1

版本：v1.0  
同步日期：2026-09-05  
用途：把網站原型轉成可由校方審查、可由學生執行、可被評審追問的低風險試辦。這不是校方同意書、法律意見或營養醫療建議；正式蒐集前仍須由學校決定核准、告知、保存與刪除流程。

## 1. 試辦要回答的問題

### 主問題

> 把菜單版本、五源秤重、餐盤初判、學生修正、匿名原因與供餐情境連在一起，能否讓學校提出更具體、可安全驗證的下一餐改善方式？

### 四項可被資料推翻的假設

1. 分開「前處理、未供出可食、盤後可食、不可食、液體／污染」後，改善位置會比單一混合總重清楚。
2. 保留 AI 原判斷與學生修正後，可以看見模型在哪些菜色或拍攝情境較容易出錯。
3. 同時記錄實到人數、菜單／食譜版本、配送情境與匿名原因後，剩食差異會比只看星期或班級更能解釋。
4. 由營養師／校方核准低風險介入並同步監測缺餐、添餐與滿意度後，可能降低可避免剩食；若安全護欄惡化，就不算成功。

## 2. 不做的事情

- 不建立學生個人完食分數、健康推論、體重或飲食排名。
- 不拍人臉、姓名、學號、座號、作業或可辨識學生的背景。
- 不把照片估計克數冒充整班電子秤實測。
- 不因學生拒答匿名原因而影響午餐、學習或評價。
- 不讓 AI 自動減餐；系統只提出可檢視的試算。
- 不以剩食率懲罰班級、學生、廚房或供餐公司。
- 不把預定清運方式寫成已發生的循環成果。

## 4. 四週設計

### 準備週（正式 Day 1 前）

- [ ] 校方指定試辦負責人、資料保存天數、存取角色與停止方式。
- [ ] 確認試辦班級、日期、學生小組與導師時段；不以學生拒答作為缺席或失敗。
- [ ] 營養師確認不調整的底線：營養規格、安全餘量、特殊飲食與現場補餐機制。
- [ ] 電子秤校正；每種容器貼代號並量皮重，寫下瀝水等待時間。
- [ ] 以 Demo 完整演練 `/workflow`、`/scan`、`/records`、`/lab`、`/forecast`、`/experiments`、`/trace`。
- [ ] 建立正式 Supabase 教師帳號與班級；確認公開 Demo 不會寫入校園資料。
- [ ] 完成一餐空流程：五源都要有紀錄，0g 也須由現場人員明確確認。

### 第 1–2 週：基準期

- 不依 FoodLens 建議改變供餐；先量出現況與操作負擔。
- 每餐至少保存：已確認菜單、實到人數、供應可食重量、五源淨重、匿名原因票數、教師情境。
- 每個供餐日抽樣若干餐盤；抽樣數與餐盤原供應重量都要保存，不把抽樣外推成全班實秤。
- 每週檢查缺漏、異常 0g、照片人工修正率與平均操作時間。

### 第 3 週：選一項低風險介入

依前兩週資料只選一個主要變因，例如：

- 份量：提供大小份或分段添飯，不直接取消安全餘量。
- 口感／食譜：調整切型、熟度、醬汁或混合方式。
- 菜色搭配：調整同餐組合，不把單一道菜的差異誤判為總量問題。
- 配送／保溫：測試送達時間、保溫或分餐節奏。
- 用餐流程：改善排隊或用餐時間，不要求強迫完食。

營養師／校方在 `/forecast` 與 `/experiments` 保存「採用、調整或維持原案」以及理由。沒有足夠相似供餐日、來源不完整或安全疑慮時，選擇「需要更多資料」也是合格結論。

### 第 4 週：改善期與複測

- 使用相同量測定義、容器、時點與資料欄位。
- 同步保存缺餐／吃不飽回報、添餐／補菜人次、1–5 分滿意度與回覆人數。
- 記錄活動、缺席、天氣、配送異常、菜單或食譜版本改變等干擾因素。
- 前後結果同時報告原始比例、下降百分點、相對改善率、班級餐期筆數與獨立供餐日。
- 前後比較不等同因果；若介入條件不同，先說明不可直接比較。

## 5. 每餐 3–5 分鐘標準流程

1. **供餐前**：導師確認實到人數；學生在 `/workflow` 核對菜單版本與實際供餐。
2. **分餐後**：以電子秤記錄實際供應可食重量；已知製作、送達或班級供應量不可互相代填。
3. **餐後**：依容器代號分別量毛重、皮重與淨重；五源每一類都有數值或待補狀態。
4. **抽樣餐盤**：只拍食物；瀏覽器完成 WebP 重編碼與 EXIF 移除後再分析。
5. **人機協作**：學生逐項核對食物類別、標準原始份量、剩餘比例與信心；確認後才保存。
6. **匿名回饋**：每人最多選一個主要原因；導師活動／配送情境另欄保存。
7. **收尾**：檢查 0g、缺漏、樣本數與單位；正式案件由現場人員完成量測覆核。

## 6. 五源秤重 SOP

| 來源           | 定義                                 | 例子           | 最容易混淆的地方                         |
| -------------- | ------------------------------------ | -------------- | ---------------------------------------- |
| 前處理廢棄     | 烹調前後在廚房產生、未成為可供餐成品 | 菜葉、修切邊料 | 不可與學生盤後剩食相加後稱為「學生浪費」 |
| 未供出可食餐點 | 已完成、仍可食但沒有分到餐盤         | 保溫桶餘量     | 應和追加備量、實到人數及供應策略一起解讀 |
| 盤後可食剩食   | 已分到餐盤、理論上可食但未吃完       | 飯、菜、肉     | 餐盤照片回答類別；整班重量仍靠秤重       |
| 不可食殘渣     | 正常不食用的部分                     | 骨頭、果皮     | 不應當成可避免剩食或要求學生吃完         |
| 液體／污染     | 湯汁、水分或已混入不可辨識污染       | 湯、含水混合物 | 未統一瀝水時間前，不宜跨日比較           |

共同規則：使用公克整數；淨重＝毛重－皮重；不可為負值；同一來源不能同時被分派到兩筆有效清運；異常先保留原始紀錄與說明，不為了圖表好看而改數字。

## 7. 學生匿名原因卡

提問固定為：「如果今天有剩，最主要的原因是哪一個？不想回答可以跳過。」

- 份量太多
- 味道／搭配
- 口感／熟度
- 溫度
- 用餐時間不足
- 其他

只保存每班各選項的合計票數。合計不可高於實到人數；不得把空白解讀成「沒有問題」。

## 8. 五組訪談題綱

每次 10–15 分鐘；先說明用途、是否記錄及可拒答。沒有完成訪談就保留空白，不製造引言。

### 學生／導師

1. 哪一步最容易做錯或最花時間？
2. 原因選項是否看得懂？哪一項缺少？
3. 拍攝與秤重是否打擾用餐或收拾？
4. 有沒有讓人覺得被責怪、比較或被要求吃完？

### 營養師／午餐秘書

1. 哪些資料足以支持小型試行？哪些資料仍不能用？
2. 供餐安全餘量、營養或特殊飲食有哪些不可突破的界線？
3. 建議需要提前幾天提出，才能進入採購或菜單流程？
4. 哪些異常會要求停止介入？

### 校方／午餐委員會

1. 誰負責資料、圖片保存、權限與刪除請求？
2. 哪些摘要可給家長，哪些資料不應離開校內？
3. 成效應如何呈現，才不會變成班級或廠商排名？
4. 什麼條件下才允許擴到年級或全校？

### 團膳／午餐公司

1. 菜單、食譜、製作量、送達量與班級供應量目前如何記錄？
2. 哪些改善能在不改變營養與合約下試做？
3. 配送、保溫、切型或批次差異如何留下版本？
4. 哪些資料會造成錯誤究責，應如何補充背景？

### 清運／處理單位

1. 可提供哪些交接、淨重、時間、設施與收據欄位？
2. 預定去向與實際收料可能在哪些情況不同？
3. 文件如何讓校方核對而不收集學生資料？
4. 重量不一致、延遲或退回時如何補正？

## 9. 每週資料品質檢查

| 指標           | 算法                                  | 合格門檻／處理                      |
| -------------- | ------------------------------------- | ----------------------------------- |
| 餐期完整率     | 完整餐期 ÷ 預定記錄餐期               | 未達 90% 先修流程，不做成效主張     |
| 五源覆蓋率     | 有明確數值或覆核狀態的來源 ÷ 應記來源 | 正式完成案件須為 100%               |
| 菜單確認率     | 已人工確認菜色 ÷ 當日菜色             | 未確認不得進入正式證據鏈            |
| 餐盤人工修正率 | 有修改的辨識欄位 ÷ 全部辨識欄位       | 只描述模型錯誤位置，不等同準確率    |
| 獨立供餐日     | 去重後日期數                          | 洞察／預測採產品內建最低門檻        |
| 未知欄位       | `null` 或待補欄位數                   | 保留未知，不以 0 或其他階段數值代填 |
| 操作時間       | 每餐開始至覆核完成                    | 若持續影響午餐秩序，縮減範圍或停止  |

## 10. 介入安全閘門

只有以下條件同時成立，才可把建議帶入下一餐試行：

- [ ] 菜單、供應重量與五源資料通過人工覆核。
- [ ] 有足夠的相似獨立供餐日；信心與降級來源已顯示。
- [ ] 建議量未突破產品 15%／8%／5% 的匹配上限。
- [ ] 營養師／校方保存採用方式與理由；AI 沒有最後決定權。
- [ ] 現場仍有補餐／添餐處理方式。
- [ ] 缺餐、添餐、滿意度與干擾因素都有量測計畫；未知保持未知。
- [ ] 若出現營養疑慮、明顯缺餐、流程負擔或隱私事件，能立即停止且不影響學生用餐。

## 11. 廚餘去向核驗

FoodLens 將四個狀態分開：

1. **預定安排**：校方打算交給哪個單位。
2. **清運交接**：實際交接時間、來源與淨重。
3. **處理端申報**：設施、實際處理方式、收料重量與外部文件指紋。
4. **校方核驗**：校方依原文件接受或填原因退回。

只有第 4 步完成才能寫「已確認去向」。收據 SHA-256 只證明系統核對的是哪一版本文件，不等同政府認證，也不證明碳排或循環效益。

## 12. 試辦停止與升級條件

### 立即暫停

- 拍到可辨識學生或個資，且無法依校方流程安全處理。
- 因介入出現明顯缺餐、特殊飲食或營養安全疑慮。
- 學生被強迫作答、完食、排名或責怪。
- 秤重定義連續不一致，資料無法合理比較。
- 工作量持續影響午餐與教學秩序。

### 可以擴到同年級

- 至少完成四週、資料完整率達門檻，且沒有以 Demo 冒充實測。
- 學生、導師、營養師與校方都確認流程可負擔。
- 至少一項介入保存完整決策、安全護欄與再量測；結果可為無改善。
- 權限、圖片保存、刪除與事件處理責任人已明確。

## 13. 送交評審的證據包

- 一張不含個資的現場流程照片或重拍示意，附日期、角色與資料身分。
- 一筆可追溯餐期：菜單版本、五源、餐盤原判斷／修正、匿名原因與人類決定。
- 一張加權比例圖，附期間、單位、餐期數與獨立供餐日。
- 一筆供餐建議及營養師／校方採用、調整或拒絕理由。
- 一組 Before／After，連同缺餐、添餐、滿意度、干擾因素與「不等同因果」。
- 一筆清運安排至校方核驗的完整或誠實未完成鏈。
- AI 使用帳：工具、用途、人工覆核、未採用內容與生成素材來源。
- 操作時間、缺漏率、人工修正率，以及至少三類利害關係人的匿名摘要。

每一張截圖與圖表都要標示「模擬情境／校園實測／估算／AI 生成素材」；沒有取得的證據留空，不以 Demo 補成真實成果。
