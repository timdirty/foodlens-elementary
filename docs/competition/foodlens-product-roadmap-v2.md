# FoodLens 食光偵探｜多角色產品路線圖 v2

版本：v2.1  
同步日期：2026-09-05（Asia/Taipei）  
定位：從 AI 餐盤分析器，升級為「校園午餐可追溯決策鏈」

## 1. 產品北極星

FoodLens 要完成的不是更多 AI 功能，而是讓一餐的證據能從規劃一路走到改善：

> 核定菜單 → 備餐配送 → 教室取餐 → 餐後量測 → 校內分流 → 清運去向 → 人類決策 → 下一餐驗證

30 秒產品說法：

> 食登平臺告訴我們今天供應了什麼；FoodLens 接著回答學生實際吃了什麼、剩下什麼、為什麼剩、最後去了哪裡，以及下一次誰可以怎麼改。AI 加速辨識與找模式，學生負責修正與說明，營養師和學校保有最後決策權。

北極星指標不是「AI 辨識率」或「廚餘總重最低」，而是：

> 在營養足夠、不缺餐、保護隱私與現場可持續的前提下，降低可避免的可食剩食。

## 4. 優先序總覽

### P0｜競賽差異化閉環

目標：讓評審看見 FoodLens 已從「辨識器」轉成可追溯、有人負責的校園決策原型。

- [x] 智慧菜單匯入、OCR 備援、標準化與人工確認。
- [x] 原訂菜單與實際供餐核對。
- [x] 五類剩食、秤重狀態及資料品質。
- [x] 學生匿名原因與班級情境分存。
- [x] 「現象 → 負責角色 → 可測試行動」決策卡。
- [x] 營養師／校方採用、調整或維持原案，保存理由與決策快照。
- [x] 預定、交接、收據與已核驗去向的可操作追溯。
- [x] Before／After 同步持久化缺餐、添餐／補菜、滿意度、營養確認與干擾因素。

P0 不包含真正的家長帳號、供餐商系統整合或政府資料串接；以有誠信的原型證明介面、資料與權責設計即可。

### P1｜單校四週試辦

目標：驗證人能否持續使用，以及照片估算與決策是否真的有幫助。

1. 1–2 個匿名班級、至少 20 個供餐日。
2. 電子秤／藍牙秤快速量測，數日與照片估算雙軌對照。
3. 供餐公司食譜版本、實際製作、配送與異常回填。
4. 一條真實清運批次與憑證核對。
5. 家長只讀匿名週報與正式回饋入口。
6. AI 修正率、估重 MAE／區間覆蓋、操作耗時及資料缺失率。
7. 至少一次由營養師核准的低風險介入與再量測。

### P2｜全校與跨校資料基礎

目標：建立可安全擴散的資料標準，而不是集中學生影像。

1. 既有菜單平臺 adapter；API 不穩時維持 CSV／Excel 備援。
2. 多校共通菜色、烹調、重量、原因與去向字典。
3. 供餐批次、食譜版本與物流資料介接。
4. 去識別化跨校自我改善基準與最低樣本門檻。
5. 政策版本、去向驗證、未知率與資料品質 Dashboard。
6. 模型漂移、不同菜色／裝置／光線的誤差與公平性檢查。

## 5. P0 功能設計與驗收標準

### P0.1 智慧菜單工作台

使用流程：匯入結構化資料 → 無資料才 OCR → 顯示原文與候選 → 人工確認 → 產生菜單版本 → 現場核對實際供餐。

必備欄位：日期、餐期、原始菜名、標準菜色、食物類別、主要食材、烹調法、食譜版本、每人標準份量、來源、辨識信心、確認者與確認時間。

驗收：

- 結構化資料永遠優先於 OCR；OCR 低信心欄位可逐項修正。
- 標準化不覆寫原始菜名。
- 同名但配方、供應商或份量不同可另建版本。
- 臨時換菜能保留原訂、實際、原因、確認者與時間。
- 未經確認的菜單不可驅動正式分析。
- 無 AI Key 時以固定範例完整 Demo，不假裝是真實 OCR。

### P0.2 來源別剩食與標準秤重

五類：`prep` 前處理、`unserved-edible` 未供出可食、`plate-edible` 盤後可食、`inedible` 不可食、`liquid-contaminated` 液體／污染。

重量欄位：毛重、皮重、淨重；`wet` 未瀝水、`standard-drained` 標準瀝水、`dewatered` 脫水後；量測法為磅秤、照片估算或人工級距。

驗收：

- 毛重小於皮重、負數、元件可食總量超過供應量時阻止送出。
- 不同重量狀態或生／熟／可食基準不可直接比較。
- Dashboard 同時顯示盤後可食率、未供出率與資料覆蓋率，不再只顯示「廚餘率」。
- 瀝水前後差異標成處理差異，不能算成源頭改善。
- 未分類重量保留為未知，不為了漂亮數據刪除。

### P0.3 原因與情境

學生匿名原因：太多、味道、口感、太冷／太熱、骨皮、不熟悉、來不及吃、不餓／有活動、其他。教師情境：實到人數異常、考試、運動／校外活動、延遲用餐、配送異常、其他。

驗收：

- 原因回饋與重量分表保存，主觀意見不能覆蓋客觀量測。
- 不要求登入學生個人帳號；不記姓名、座號、學號或健康資料。
- 可跳過原因；不以獎懲提高填答率。
- 每個洞察都顯示回饋份數與量測覆蓋率。
- 單一或低樣本回饋不生成結論。

### P0.4 責任導向決策卡

卡片固定包含：觀察、證據、可能原因、需補資料、建議負責角色、可測試行動、營養／安全護欄、信心與樣本。

驗收：

- 高未供出量優先送到人數／備餐問題；高盤後量才分析份量、食譜與用餐情境。
- 蔬菜高剩食不產生「刪除蔬菜」建議。
- 配送異常不歸咎學生。
- 每張卡可展開到具體餐期、計算公式與原始證據。
- 使用者可以標記「採用／需更多資料／不適用」。

### P0.5 人類決策與改善護欄

營養師／校方決策：接受建議、調整後採用、維持原案；必填理由、實施日期、負責人、預計檢查日期。

驗收：

- `recommendation` 與 `humanDecision` 是兩筆不同資料。
- UI 永久顯示「決策建議，仍由營養師或學校決定」。
- 低樣本時降級或不提出減量；任何建議受既有 15%／8%／5% 上限約束。
- 改善實驗同時檢查可食剩食、添餐、缺餐、滿意度及營養確認。
- 結果顯示下降百分點與相對改善率；不將前後差異寫成因果。

### P0.6 去向追溯最小切片

先做能說清楚狀態的介面，不宣稱已串接清運系統。

驗收：

- 保存校內交付淨重、清運者、預定去向、實際收受去向、憑證編號、查核狀態及政策生效日。
- 預定去向與已驗證去向視覺上不可混淆。
- 沒有憑證顯示「待確認」，未知重量保留在分母。
- 系統不自動判定合法性，也不宣稱 100% 循環或零碳。
- Demo 憑證必須標示為模擬，不可使用真實機構名稱冒充合作。

## 6. 資料模型 v2：以新增與版本化取代破壞性重寫

目前 `MealRecord`、`PlateScan`、`ScanDetection`、`ScanCorrection`、`SupplyPrediction` 與 `ImprovementExperiment` 已能支撐既有 Demo。v2 採新增資料表與外鍵的方式擴充，保留舊資料可讀，待轉換完成才淘汰單一 `leftoverG` 語意。

```text
menu_versions
  └─ menu_items
       └─ meal_batches
            ├─ meal_contexts
            ├─ feedback_events
            ├─ waste_measurements
            │    └─ plate_scans → detections → corrections
            ├─ supply_predictions → human_decisions
            │                         └─ interventions → outcomes
            └─ collection_events → destination_receipts
```

### 新增實體

| 表                          | 最重要欄位                                           | 不變條件                 |
| --------------------------- | ---------------------------------------------------- | ------------------------ |
| `menu_versions`             | 原始來源、狀態、版本、核定者、生效時間               | 核定後內容不可靜默覆寫   |
| `menu_items`                | 原始／標準菜名、類別、食材、烹調、配方版本           | 原文永久保留             |
| `meal_batches`              | 預計／通知／實際人數、製作／配送／盛裝量、重量基準   | 不同基準不可直接運算     |
| `meal_contexts`             | 活動、用餐時間、配送／溫度異常                       | 與學生原因分開           |
| `feedback_events`           | 匿名原因、菜色、可選備註、資料身分                   | 無個人識別碼             |
| `waste_measurements`        | 來源、毛／皮／淨重、瀝水狀態、方法、樣本／覆蓋、污染 | 所有重量整數克；保留未知 |
| `human_decisions`           | 建議、採用模式、實際量、理由、決策者、日期           | 不修改原始建議           |
| `interventions`／`outcomes` | 介入、比較條件、護欄與結果                           | 結果保留不確定性         |
| `collection_events`         | 清運者、交付時間與淨重                               | 不推定實際去向           |
| `destination_receipts`      | 預定／實際路徑、收受重量、憑證、驗證狀態、政策版     | 無憑證即未驗證           |

所有 operational tables 必須有 `school_id`、`source_kind`（demo／measured／estimated／official）、建立者與時間；正式資料維持 RLS，多校外鍵使用 `(school_id, id)` 防止跨校關聯。

### Repository 介面現況

UI 仍只依賴 `FoodLensRepository`，DemoLocal 與 Supabase 實作相同方法：

```ts
interface FoodLensRepository {
  getSnapshot(): Promise<AppSnapshot>;
  confirmScan(
    command: ConfirmScanCommand,
  ): Promise<{ mealId: string; scanId: string }>;
  savePrediction(prediction: SupplyPrediction): Promise<void>;
  saveExperiment(experiment: ImprovementExperiment): Promise<void>;
  saveEvidenceCase(
    evidenceCase: MealEvidenceCase,
  ): Promise<{ mealRecordId: string }>;
  saveCollectionEvent(event: CollectionEvent): Promise<void>;
  saveDestinationReceipt(receipt: DestinationReceipt): Promise<void>;
  // 班級、研究、設定、備份與保存期限操作亦在同一介面
}
```

`saveEvidenceCase` 將菜單、餐期批次、五源量測、匿名回饋與人類決定當作一個原子寫入邊界；DemoLocal 與 Supabase 都實作相同介面。新能力仍必須先由 Zod schema 定義輸入與 invariants，再同步更新兩個 repository、Supabase migration、RLS 與測試；不在各頁以 `mode === ...` 分散判斷寫入後端。

## 7. 路由與資訊架構影響

| 路由                     | P0 改動                                                        | 不應塞入的內容                   |
| ------------------------ | -------------------------------------------------------------- | -------------------------------- |
| `/` 控制中心             | 將單一剩食拆為盤後／未供出／資料覆蓋；加入「目前最該由誰處理」 | 不放八角色全部細節               |
| `/workflow` 一餐任務台   | 菜單、五源、原因、決策與證據鏈完成狀態                         | 不用單一人代填所有上下游事實     |
| `/scan` AI 掃描          | 先選已確認菜單；新增匿名原因；完成頁連到證據鏈                 | 不在學生流程要求供餐商欄位       |
| `/records` 每日紀錄      | 每餐展開計畫、實際、五類剩食、修正與去向狀態                   | 不以一張巨表同時編輯全部資料     |
| `/lab` 數據實驗室        | 新增來源別漏斗、原因×菜色、配送×剩食、資料品質                 | 不做班級／廠商羞辱排行           |
| `/forecast` 智慧預測     | 顯示菜單版本與護欄；新增正式人工決策工作流                     | 不允許 AI 直接確認訂單           |
| `/experiments` 改善實驗  | 介入類型、責任人、護欄結果與干擾因素                           | 不把相對改善寫成因果             |
| `/impact` 永續影響       | 分開源頭避免與處理減重；新增去向驗證率                         | 無來源前不放全球單一碳因子       |
| `/trace` 去向追蹤        | 五源逐批安排、交接、處理端申報、校方核驗與退回                 | 未核驗時不宣稱實際去向或循環成效 |
| `/research` 專題研究     | 八角色、量測定義、資料治理與 AI 揭露                           | 不宣稱尚未做的訪談或合作         |
| `/admin` 教師管理        | 菜單匯入、原因字典、重量規則、保留期、去向字典                 | 不讓一般學生看到合約／憑證       |
| `/presentation` 評審模式 | 以「一餐證據鏈」取代功能導覽；固定 Demo 情境                   | 不在 8 分鐘內展示所有後台表單    |

首版決定不為角色數量繼續增加路由：單一餐期證據收旂於 `/workflow` 與 `/records`；建議、人類採用理由與再量測狀態收旂於 `/forecast` 與 `/experiments`。等實際單校試行證明工作佇列需求，才考慮獨立角色工作區。

## 8. 分析引擎 v2

### 描述

- 盤後可食剩食率。
- 未供出可食率。
- 總可避免浪費率。
- 每位實際用餐者剩食克數。
- 量測覆蓋率與未知率。

### 診斷

- 菜單版本、烹調法、星期、班級情境、配送、原因回饋與來源別剩食交叉比較。
- 門檻沿用「星期／班級至少 3 筆、類別至少 5 筆、差異至少 5 個百分點」，並依分析類型另加覆蓋率要求。
- 洞察文字必須可展開查看分子、分母、樣本與排除條件。

### 預測與建議

- 現版輸出單一建議參考量；下一版需先建立足夠真實校正資料，才把它升級成有方法依據的「需求區間」，兩者都不是精確訂購量。
- 仍以最近 180 天、相同版本 3–8 個獨立日期優先，降級至相似菜色與全校基準。
- 除歷史平均外，顯示每日波動、資料新鮮度、量測品質、食譜是否變更。
- 行動規則先判斷問題來源，再決定送給教室、營養師、廠商或校方。

### 驗證

- `盤後可食率下降百分點 = 基線率 − 改善期率`。
- `相對改善率 = 下降百分點 ÷ 基線率`。
- 同時顯示每生克數、缺餐、添餐、滿意度、營養確認及覆蓋率。
- 條件差異大時只說「觀察到變化」，不宣稱因果。

## 11. 明確不做

- 不做個人完食分數、臉部辨識、學生飲食側寫或班級羞辱排行。

- 不把供餐商廚餘總重當成學生盤後剩食。

- 不把瀝水減重包裝成源頭減少。
- 不將 48／96 筆 Demo 稱為真實大數據。

- 不在沒有處理憑證時宣稱合法去化、循環利用或零廚餘。

## 12. 評審最可能追問與一句回答

1. **磅秤和 Excel 不就好了？** 磅秤仍是重量基準；FoodLens 的價值是把菜單、分類、原因、人類決策與下一次結果接起來，AI 只降低每天整理的負擔。
2. **照片怎麼知道幾克？** 我們不宣稱照片能精確秤重；照片只提供剩餘比例與推估值，班級總量以扣皮重的電子秤為準。
3. **48 筆是真資料嗎？** 不是；它們是固定、醒目標示的模擬資料，只用來證明流程與公式可操作。
4. **你們的創新不就是辨識食物？** 辨識只是入口；真正創新是從核定菜單一路追到人類決策、再量測與去向證據。
5. **會不會讓學生吃不飽？** 系統不自動減餐，建議有上限、安全備餐與營養師核准；樣本不足就不建議減量。
6. **怎麼證明改善是 FoodLens 造成？** 初版不宣稱因果；用相同定義、相似菜色、前後樣本與干擾因素檢查關聯，條件允許再設對照。
7. **廚餘最後去哪裡？** 不從政策推定；預定去向與實際憑證分開，沒有憑證就保持待確認。
8. **如何擴校又保護學生？** 跨校傳遞去識別化衍生資料與品質指標，不集中學生照片，小樣本不公開，也不做個人或學校羞辱排名。

最後的產品判斷原則：**凡是不能回答「資料從哪來、誰能決定、如何驗證、可能傷害誰」的功能，就不應因為看起來有 AI 而優先開發。**
